# Slab audit, 2026-07-29

Target: `atomicsite/` (published as Slab at github.com/bright-interaction/slab), 123k LOC Go plus a SvelteKit admin and an Astro SSG build, 146 MCP tools. Base `origin/main` @ `905d35f4`; `atomicsite/` is byte-identical at `748b468a`, so the base stayed valid when main moved mid-run.

Fixes are on `agent/slab-dep-fixes-2026-07-29`, merged to `main` and **DEPLOYED to production 2026-07-30** (main `73a2ddc3`, `deploy-atomicsite` succeeded, image built 09:31:46Z). All six lenses ran; every finding at every severity is fixed or explicitly refuted; gates fully green.

Deploy verified by behaviour, not by pipeline status: `GET /api/health` returns the new `crm_outbox_pending` field (so the new binary is live), `crm_outbox` exists in the production database (so `applySchema` applied the schema change at boot), and the boot log shows `shield enabled on MCP boundary` (so the new config validation did not block startup).

Two pre-deploy checks decided it was safe to ship the tenant-visible changes: `ATOMICSITE_SHIELD_REDIS_URL` is unset in production, so the new fail-closed validator never fires, and `ATOMICSITE_CLOUDFLARE_ZONES` is unset with zero `site_domains` rows, so the new DNS-TXT ownership gate cannot break an existing domain.

## Run integrity

```
agents spawned: 14 (1 scout + 6 lenses + verifiers), across 4 attempts
returned usable: 7 (scout, Lens A partial, and Lens B/C/D/E/F in full)
verifiers run:  0 by the crew, every finding verified by hand instead
```

**The first crew run collapsed.** Every lens, most verifiers and the supervisor itself died to `stalled: no progress for 600s` or `Connection closed mid-response`. Only Lens A produced output, and its verifiers died mid-flight. This is the failure mode Mesh already records as "a multi-agent audit whose agents ALL died returned safe_to_publish=true": a dead crew is not a clean codebase. The run was restarted in 2-agent batches with instructions to emit findings incrementally, which held.

Because the verification stage never ran, **every finding below was verified by hand** before being fixed. That mattered: of the 5 leads recovered from the dead Lens A, **2 were refuted**.

## Verdict

Not shippable as it stood. Four independent paths to full compromise, three of them reachable by an ordinary authenticated tenant. All four are fixed. The isolation core is genuinely solid (see SOLID); the defects clustered in three places: **code that the 2026-07-17 fix pass introduced and nobody re-reviewed**, **guards applied to one surface and not its twin**, and **denylists used where the set they exclude keeps growing**.

## P0, fixed

### 1. CRITICAL. A tenant's build could read the object-storage credentials for every tenant's database

`internal/builder/compiler.go` (env) chained with `internal/builder/blocks_extra.go:1630,1656` (sink)

Two findings that only matter together:

```
tenant writes a custom / raw_astro block   -> no sanitization on 2 of 3 sinks
  -> output lands in the generated .astro SOURCE
  -> {expr} is build-time JavaScript, evaluated by Astro in Node
  -> reads process.env
  -> LITESTREAM_SECRET_ACCESS_KEY -> S3 replica of EVERY tenant's SQLite DB
```

`buildEnv()` was a denylist: a name list plus a "secret-shaped suffix" heuristic. `LITESTREAM_SECRET_ACCESS_KEY` ends in `_ACCESS_KEY`, and the checked suffixes are `_API_KEY` and `_APIKEY`. `LITESTREAM_ACCESS_KEY_ID` ends in `_ID`. Both are set on the server process by `docker-compose.yml:43-44`. Verified by running the real predicate: both report `LEAKS to build` while `JWT_SECRET` is correctly stripped. `BRIGHTCRM_WEBHOOK_SECRET_PREVIOUS`, `FLARE_DSN` and `ATOMICSITE_SHIELD_REDIS_URL` leaked identically.

`sanitizeRawHTML` had exactly one call site (`raw_html`), while `custom`.markup and `raw_astro`.code emitted the tenant string verbatim. The justifications were circular: `blocks_extra.go` said the block-time guardrail was the defense, `guardrails.go:81-87` said the render-time bluemonday pass was authoritative. Neither ran on these two.

Fix: `buildEnv` inverted to an allowlist (a denylist over a growing environment cannot be made correct); both sinks sanitized; `raw_astro` output additionally brace-neutralised, because braces are ordinary text to an HTML sanitizer and CSP does not apply to build-time evaluation.

### 2. CRITICAL. A tenant could obtain a real TLS certificate for an operator hostname

`internal/domains/cloudflare.go:107`, `internal/domains/reconciler.go:226` vs `:234`, `internal/handlers/domains_verify.go:39`

In a Cloudflare zone the operator manages, the flow proved ownership to itself. `EnsureA` runs **before** `VerifyHostnameOwnership` and its error is non-fatal. `listRecords` queried `?type=A`, and the "never overwrite an untagged record" guard from 2026-07-17 only ran inside the loop over existing A records, so with no A record the function fell through to `createRecord` unguarded. `VerifyToken` resolves by token alone and never compares `r.Host` to `row.Hostname`. So: claim a name, we point it at our own edge, we verify our own handiwork, certbot validates over the record we just created. `GET /domains/help` even hands over the zone list and edge IP.

Adding a Host check does **not** fix this: the probe legitimately carries `Host: <target>`.

Fix: inside a managed zone, require a TXT proof at `_atomic-verify.<hostname>` before any DNS write, fatal on failure. Scoped to managed zones, so the ordinary custom-domain flow is unchanged. The Domains page previously said "We're auto-creating the A record", which would have become a lie; it now shows the exact TXT record.

### 3. CRITICAL. A Mollie outage permanently zeroed stock

`internal/handlers/orders.go:557` vs `:837`

Checkout commits the reservation tx and then calls Mollie. The undo was missing: any failure to create the payment left the order at `pending` with an empty `payment_id`, no webhook ever arrives for those, and the release path only ran from the `failed` webhook. Stock and the discount `max_uses` slot were consumed permanently by an order nobody paid for.

Fix: a reaper keyed on `payment_id = ''` so it only touches orders that never reached Mollie, plus a release hook on `pending -> cancelled`.

### 4. HIGH. SSRF into the live Tailscale tailnet

`internal/migration/safefetch.go`, `internal/webhook/ssrf.go`, `internal/domains/ssrf.go`, `internal/handlers/media.go`

Four packages, four copies of the same predicate, one shared hole: `net.IP.IsPrivate` covers RFC1918 and `fc00::/7` but not RFC 6598 CGNAT, `100.64.0.0/10`, which is the Tailscale range. Verified against the real predicate:

```
100.100.100.100      blocked=false   <- estate tailnet host
100.100.100.101     blocked=false   <- estate tailnet host
64:ff9b::7f00:1  blocked=false   <- NAT64 wrapping 127.0.0.1
169.254.169.254  blocked=true
```

Both those addresses are in `scripts/mirror-redactions.txt` precisely because they are real estate infrastructure. Fix: one `internal/netguard` requiring `IsGlobalUnicast` first, so unlisted ranges fail closed. Four copies replaced by one, since the drift between them was the root cause.

### 5. HIGH. A plain member could self-grant control of the site's CSP

`internal/handlers/agent.go:1112`, `internal/handlers/allowed_scripts.go`

`GenerateAgentKey` had no role gate and stored `req.Capabilities` verbatim, and that list **is** the authorization set the MCP dispatcher reads. A member could mint themselves `security`, which gates CSP allowlist mutation, and add an attacker origin to `script-src`. The MCP gate justified itself with "CSP allowlist mutation is admin-only on REST"; `allowed_scripts.go` had **zero** role checks, so that was false.

Fix: `RequireOwnerOrAdmin` on key mint/revoke/bootstrap and on the allowed-scripts mutations, a closed `KnownCapabilities` vocabulary, and the comment now names what enforces it.

### 6. HIGH. Cross-tenant agent-key revoke

`internal/handlers/agent.go:1177`

`siteID` was read from the URL and never used; the query was `UPDATE agent_keys SET is_active = 0 WHERE id = ?`. Route site-scoped, query not. Fixed at the query layer, which is the layer a future handler cannot get wrong. Lens C found this independently after I had fixed it, which is a confidence signal rather than a duplicate.

### 7. HIGH. SSO bypassed TOTP, accepted unverified emails, and auto-provisioned admins

`internal/handlers/oidc.go`

Three in one surface. `email_verified` was parsed at line 67 and **read nowhere in the codebase** (one grep hit, the declaration). Auto-provisioned SSO users got `Role: "admin"`, which is a global superuser here: `site_access.go:101,169` and `workspace_access.go:210` all short-circuit on it, so every auto-created SSO account held every site and workspace. And the callback minted a session without checking TOTP, so a user who deliberately enrolled had it enforced on the password path and skipped on SSO.

Fix: tri-state `email_verified` (absent and false are different answers, so issuers that omit it still work); `OIDC_DEFAULT_ROLE` defaulting to `editor` and failing closed; an MFA-pending flow with the SPA screen to complete it.

### 8. HIGH. The mirror enterprise-strip gate had three defects at once

`atomicsite/scripts/split-public-repo.sh:131`

```
SIGPIPE fail-open:  fired at 20/60/100 planted files, CLEAN at 200 and 400
HEAD-only scan:     the mirror publishes history, not HEAD
literal `ee` match: missed a standalone //go:build pro
```

It also false-refused on prose merely mentioning the tag. This was the only mirror gate with no test, and it guards the whole commercial moat.

**Not a live leak.** Lens B reported EE source published in the mirror's history. I scanned every blob in the public repo: **0 enterprise-tagged files across 3005 Go blobs in 618 commits**. Those paths (`internal/cloud/billing`, `internal/cloud/edge`) live only on branch `moat/slab`, which is not an ancestor of `main`, and the split script publishes from `main`. A pre-merge landmine, not an exposure. It would have fired the first time `moat/slab` merged.

Fix: both paths added to `STRIP_PATHS`, the guard rewritten to capture-and-test-content, walk history, and match `ee|pro`. New `scripts/test-mirror-enterprise-check.sh` wired into pre-commit; it reports 4 failures against the pre-fix guard.

### 9. HIGH. Refund was check-then-act across a network call

`internal/handlers/orders.go:220-258`. Double-click or dashboard retry: both read `paid`, both passed `canTransition`, both created a full refund at Mollie, only the last `refund_id` persisted. Fix: claim locally with a guarded UPDATE first, 409 on 0 rows, un-claim if Mollie then fails.

### 10. HIGH. Unbounded map, remotely triggerable

`internal/crmsync/throttle.go:52`. Every public `/t/*` request with a fresh `visitor_id` added a permanent entry. ~120 bytes each, so 10M requests is over a GB of unreclaimable heap and an eventual OOM with no correlated spike, because the map rebuilds empty on restart. The per-IP limiter does not bound it (keyed on IP, not visitor). Fix: inline sweep under the existing mutex.

### 11. HIGH. The REST block API bypassed the guardrail engine entirely

`internal/handlers/blocks.go`. `ValidateBlock` ran on the agent and MCP surfaces only, so the payload rejected by `create_block` over MCP was accepted by `POST /api/pages/{id}/blocks`. Combined with finding 1's unsanitized sinks, that path had no input check and no render check. Fix: wired into Create, Update (on the resolved payload, since a partial update can turn an innocuous block into a violating one) and BulkSave (before the destructive delete, so a violation on block 7 cannot leave the page cleared).

### 12. Supply chain, four items

`bun.lock` was missing from the embedded Astro skeleton, so `--frozen-lockfile` could never succeed and **309 packages resolved live from npm on every tenant build**. `//go:embed all:skeleton` has no exclude syntax, so a stray `bun install` bakes node_modules into the binary and the public mirror. Litestream was installed as root via wget + `dpkg -i` with **no integrity check anywhere in the image build**. bun came from floating tags. All fixed; the Litestream pin is trust-on-first-use and says so, since upstream publishes no checksums.

### 13. MEDIUM, fixed

`atomicsite://members` sent every collaborator's real name to the LLM in the clear (the shield's key map excludes bare `name` deliberately, and there is no name regex because a name is not pattern-matchable). A malformed `ATOMICSITE_SHIELD_REDIS_URL` disabled the shield for the container's life with one log line. Shield failed **open** on `resources/read` and `prompts/get` while `tools/call` failed closed. Frontend advisories to zero.

## Refuted

Verification earned its place here. These were reported and are **not** real:

- **clientIP spoofing bypasses the rate limiter.** `server.go:160` mounts `authmw.TrustedProxyRealIP`, which honours XFF only from trusted peers and explicitly replaces chi's stock RealIP. (The comment at `fingerprint.go:139-142` is stale and says otherwise; behaviour is correct.)
- **Invite tokens exposed.** `/api/admin/invites` is inside `RequireAdmin`. Admins holding invite URLs is the design.
- **EE source live in the public mirror.** See finding 8. Zero enterprise blobs public.

## Cross-project pattern: the incomplete migration, again

This shape appeared **eleven** times across the lenses: a guard applied to one surface and not its twin. Findings 5, 6, 8, 11 and 13 here, plus Lens D's three retention omissions and Lens E's five. It is already documented in Mesh and in CLAUDE.md section 15, and it keeps recurring.

The second pattern worth naming: **three of the worst findings were denylists** (`buildEnv`, the SSRF predicate, `isInternalMCPError`) where the excluded set keeps growing. A denylist over an open set is wrong by default. Two are now allowlists.

## Still open, not fixed

Nothing from any of the six lenses. Every CRITICAL, HIGH, MEDIUM and LOW finding is either fixed or explicitly refuted.

One item was closed by REFUTATION rather than a fix, recorded here so it is not re-investigated: GDPR erasure and the DuckDB store. `sql.Open("duckdb", "")` has an empty DSN, so that engine holds no data of its own, and the ATTACH is read-only. The SQLite cascade IS the erasure and DuckDB reads through to the same file. Documented at `internal/analyticsdb/analyticsdb.go` along with what would make it a real gap again (giving the DSN a path, or materialising a DuckDB table instead of querying the ATTACHed schema).

Two items were resolved differently than the lens proposed, on purpose:

- `personalization.Eval` was proposed for deletion. Kept and marked instead, because deleting a function the package doc advertises invites someone to reimplement it worse. Its four measured divergences from the shipping JS are now pinned by a test. Writing that test surfaced an error in the finding itself: `isEmpty` has a `float64` case and no `int` case, so an `int` 0 does not diverge while `float64(0)` does, and `float64` is the one that matters because `encoding/json` produces it.
- The estate GitHub token in the publish container is now **half fixed in code, half an operator task**, which is the honest split. The code half is done: the token is written to a 0600 file in the run's keydir and mounted, instead of being exported into the container environment, so the `go test ./...` that `split-public-repo.sh` runs on the filtered tree no longer inherits an org-wide credential. The resolver also prefers `MIRROR_PUBLISH_TOKEN` over the estate `GITHUB_TOKEN`, so dropping in a fine-grained token scoped to the four mirror repos needs no code change. Minting that token is the remaining operator action, and until it exists the estate token is still the fallback, because a publish that cannot push `.github/workflows/` is worse than a wide token used for one command.

## SOLID

Verified to hold, so the next audit does not re-burn it.

- **MCP tenancy, exhaustively.** All 114 registered tools enumerated, 172 `s.queries.*` call sites intersected against queries with no `site_id` predicate; the 46 by-id sites that remained all enforce scope. A scripted scan for the `RevokeAgentKey` shape across all of `internal/store` (a `Params` struct carrying `SiteID` where the SQL never references `site_id`) returns **0 hits**.
- **The 2026-07-17 commerce reservation core is correct.** Transaction boundary, guarded UPDATEs, webhook compare-and-set idempotency, amount and currency pinning, and double-release protection all genuinely right. Every defect found was at an edge that leaves `pending` without the `failed` webhook.
- **The bluemonday policy is strong.** All 13 named vectors neutralized (`data:image/svg+xml;base64` with onload, `javascript&colon;`, `iframe srcdoc`, CSS `expression()`, `svg use href`, MathML, `meta refresh`, `base href`). The policy was never the weak link; its coverage was.
- **Both renderers share the block path**, so there is no Go-preview vs Astro-build divergence at block level.
- **The 2026-07-17 fixes all hold**: JSON-LD template-literal XSS, the cross-tenant delete, MCP error scrubbing, MCP capability caps, order-PII-over-MCP, migration SSRF with the dial-time rebinding hook across all four crawl paths, `use_app` redirect credential egress.
- **Money is integer minor units end to end**, no float in the price path, mixed currencies rejected, refunds cannot exceed the original.
- **Workspace isolation and build serialization**: full `RemoveAll` per site, per-site mutex plus global semaphore, failed builds do not partially publish.
- **Production boot guards** refuse default/short `JWT_SECRET`, default `ANALYTICS_SALT`, a non-32-byte shield key, non-HTTPS `BASE_URL`, and `cloud` mode on an OSS binary.
- **`internal/sharedsecret` is correct and fail-closed**; the frontend SPA has exactly one `{@html}` and it is safe.
